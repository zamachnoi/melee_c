WebGL2 replay renderer

A staged replacement for server-rendered replay frames
Decision: WebGL2 production renderer · C remains parser, extractor, and visual reference
Plan date: 2026-08-16 · Asset schema baseline: 4
Outcome. A replay downloads state and reusable assets once, then plays and scrubs locally at a deterministic 60 Hz. WebGL2 renders the stage, animated fighters, items, and effects. Camera movement is instant and never reaches the server. Completed replays use a compact HTTP snapshot; live games use batched WebSocket state updates. The existing C software renderer remains available only as a reference until visual parity is proven.

Success means

  • No /api/frame or /api/frames during normal playback.
  • Exact 60-frame simulation progression.
  • Free pan/zoom, original camera, fit, and player-follow modes.
  • Completed replay payload measured in MB, not hundreds of MB.
  • Reusable assets cached across matches.

Not in the first slice

  • WebGPU backend.
  • All 26 characters and every stage.
  • Perfect TEV/material emulation.
  • Particles and every item model.
  • Deleting the C renderer before parity.

01Measured baseline and reason for the rewrite

Deflate13.19 ms average, 23.17 ms maxRepeated compression is expensive and scales per viewer.

02Decisions that should not drift mid-implementation

#DecisionReason
D1WebGL2 is the first production GPU backend.Broad support, mature tooling, and ample performance for this scene size.
D2Completed replay state is fetched once over HTTP.A finite replay is a cacheable object; it should not require a live socket.
D3WebSocket is reserved for live/in-progress games.It carries newly committed frames, replacements from rollback, and game-end state.
D4C remains authoritative during migration.The browser implementation is verified against known C state and reference images.
D5CPU evaluates bones first; vertex shader skins.Simple to validate. GPU compute is unnecessary for a few fighters.
D6Existing schema-4 assets are parsed directly first.They are versioned, pointer-free, big-endian, and already contain GPU-ready source data.
D7Integer replay frame is the source of truth.Avoids floating-point drift and ties HUD, animation, seeking, and rendering to one index.
D8The old frame API is removed only after parity gates pass.Keeps a working viewer and a visual oracle throughout the rewrite.

05Completed replay timeline contract

Add a versioned binary endpoint, conceptually:

GET /api/replay?f=upload_test.slp
Content-Type: application/vnd.melee.timeline
Content-Encoding: br
ETag: "replay-hash:timeline-schema"

header
  magic[4]           "RPL2"
  schema             u16
  flags              u16
  start_frame        i32
  end_frame          i32
  stage_id           u16
  slot_count         u8
  section offsets    u32...

players[]             identity, character, costume, display metadata
slot_presence[]       bitset per frame
player_frames[]       fixed-size records, indexed by slot + frame
items[]               sparse records grouped by frame
stage_events[]        sparse FoD / Whispy / Stadium events
camera[]              optional original-camera samples

Per-player frame — first schema

FieldTypeUse
animation indexu16Select action/clip without name lookup.
action stateu16HUD/debug and fallbacks.
animation framef32Track sampling input.
x, yf32 × 2Authoritative world root.
facingf32Horizontal model projection/mirror.
percent, shieldf32 × 2HUD and shield effect.
stocks, flagsu8 × 2Visibility and state flags.
Size target: a normal two-player completed timeline should be comfortably below 2 MB compressed. Measure before optimizing field widths further.

Protocol rules

  • Every multibyte field has documented byte order and alignment.
  • Unknown trailing sections are skipped using offsets/lengths.
  • Schema mismatch fails visibly; never reinterpret bytes optimistically.
  • The endpoint is immutable for a completed replay and supports ETag caching.
  • JSON is retained only for small manifests and human-readable errors.

06WebSocket live-state protocol

WS /api/live?f=current.slp

client → HELLO { supported_schema, resume_sequence }
server → SNAPSHOT { replay header + recent committed range }
server → FRAMES   { sequence, first_frame, count, binary records }
server → REPLACE  { sequence, first_frame, count, binary records }
server → GAME_END { final_frame, reason }
either → PING/PONG
server → ERROR    { code, message }

Correctness requirements

  • Sequence numbers are monotonic. A gap triggers snapshot recovery.
  • REPLACE overwrites prior state by frame number; latest rollback version wins.
  • Messages batch frames. Never emit one WebSocket message per player per frame.
  • Reconnect resumes by sequence when possible and falls back to a snapshot.
  • The client exposes buffer depth but does not couple render timing to socket timing.
  • Backpressure has a bound; stale intermediate updates may be consolidated into a fresh snapshot.

07GPU asset delivery and parsing

The existing cache format is suitable for the first browser implementation. It is explicitly serialized big-endian and already contains bones, vertices, weights, indices, primitive groups, materials, textures, animations, and stage sections.

Immutable routes

/assets/v4/models/fox-0.model
/assets/v4/anims/fox-0.anims
/assets/v4/stages/fd.stage

Cache-Control: public, max-age=31536000, immutable
ETag: content hash

Browser parsing strategy

  • Use ArrayBuffer + DataView for big-endian headers and records.
  • Copy final arrays once into native typed arrays suitable for gl.bufferData.
  • Validate counts before allocation and reject truncated/oversized inputs.
  • Upload raw RGBA textures directly first; atlas/compressed texture work is deferred.
  • Key the in-memory asset cache by schema, character, and costume.
Do not optimize the wire format early. Prove one exact Fox/Falco/FD vertical slice with schema 4. Introduce atlases or KTX2 only after measuring actual asset transfer and GPU memory.

08WebGL2 render architecture

GPU resources per model

Material tabletexture, diffuse, alpha, flags, draw rangeAsset lifetime
Bone textureCurrent matrices as RGBA32F texelsUpdated per pose

Pass order

  1. Backdrop clear/gradient.
  2. Opaque stage sections with depth writes.
  3. Opaque fighter primitive groups with depth writes.
  4. Items and simple effects.
  5. Transparent primitive groups, sorted at group granularity.
  6. Shields and debug overlays.
  7. HTML HUD outside WebGL.

Required GL state discipline

  • One renderer-owned state cache; application code never calls raw GL.
  • Explicit state setup per pass: program, VAO, depth test/write, blend mode, cull mode.
  • Development builds check gl.getError() at pass boundaries.
  • Handle webglcontextlost and rebuild all resources after restoration.
  • Use device-pixel-ratio-aware canvas sizing with a configurable upper bound.

Projection mapping to preserve

The first shader must match render_pose_profile, not invent a new view:

  • Model Z contributes horizontal screen position.
  • Model Y contributes vertical screen position.
  • Model X supplies painter/depth ordering.
  • Negative replay facing mirrors the profile horizontally.
  • Replay x/y is the authoritative fighter root; animation root locomotion is not double-applied.

09Animation evaluation and GPU skinning

CPU pose evaluation — port in this order

  1. sample_key: step, linear, and guarded cubic Hermite.
  2. sample_joint: base SRT decomposition followed by animated channel overrides.
  3. eval_pose: local matrices followed by parent-to-child world matrices.
  4. Rigid versus weighted skin matrix preparation.
  5. Upload matrices to the fighter's floating-point bone texture.

Vertex shader contract

#version 300 es
in vec3 a_position;
in vec2 a_uv;
in vec4 a_color;
in vec4 a_weights;
in uvec4 a_bones;

uniform sampler2D u_boneMatrices;
uniform mat4 u_viewProjection;
uniform vec2 u_replayRoot;
uniform float u_facing;

// Fetch 3x4 affine matrices, blend by weights, preserve rigid-vertex rule,
// convert model profile axes to replay world axes, then apply camera.

Validation invariants

  • Animation frame quirk (frame <= 0 ? 1 : frame + 1) matches C.
  • Loop wrapping matches action end_frame.
  • Root animation translation is suppressed where replay x/y is authoritative.
  • Facing changes only the intended profile axis.
  • Missing animation uses an explicit, tested fallback.

10Camera, controls, and exact frame clock

Camera state

{
  mode: "free" | "melee" | "fit" | "follow" | "stage",
  centerX: number,
  centerY: number,
  zoom: number,
  targetPort: number | null,
  smoothing: number
}

Controls

  • Pointer drag: pan.
  • Wheel/pinch: zoom around cursor.
  • Double click: reset to selected mode.
  • Number keys: follow player.
  • Mode button: free, original Melee, fit players, stage, follow.
  • Camera control remains active while paused and while scrubbing.

Clock rules

elapsed = now - playbackStartedAt
frame = anchorFrame + floor(elapsed * 60 / 1000)
frame = clamp(frame, startFrame, endFrame)
  • Never repeatedly add 1000/60; derive from the anchor to avoid drift.
  • Seeking sets an integer frame and resets the time anchor.
  • On 120/144 Hz displays, a state may render more than once; simulation remains 60 Hz.
  • If one presentation is missed, jump to the correct current replay frame rather than slowing simulation.

11Implementation phases and hard exit gates

Phase 0 — Golden fixtures and contractsNo rendering yet
  • Select representative frames: idle, run, attack, shield, airborne, facing flip, rollback, Nana.
  • Record C frame state and reference images for Fox/Falco on FD.
  • Write timeline schema and WebSocket message specification.
  • Define renderer interface and camera coordinate conventions.
Exit gate: fixtures and byte-level contracts are reviewed before browser implementation starts.
Phase 1 — State and asset deliveryNo pixel streaming
  • Add completed timeline serializer and endpoint.
  • Add immutable, allowlisted asset routes.
  • Implement browser parsers for model, animations, and stage.
  • Compare browser-decoded records with C structs across fixtures.
  • Add payload size and parse-time measurements.
Exit gate: browser loads all state and assets for a replay; sampled values exactly match C; timeline is under the agreed size target.
Phase 2 — Static WebGL2 vertical sliceFox/Falco/FD
  • Create context, resize policy, error boundary, and resource lifecycle.
  • Upload one fighter model and draw bind pose with textures.
  • Draw accepted FD sections and backdrop.
  • Implement free pan/zoom camera.
  • Match C projection, facing, materials, alpha, and depth.
Exit gate: static reference poses and stage pass image-diff tolerance; camera movement makes zero network requests.
Phase 3 — Animation and deterministic playback60 Hz
  • Port key sampling, SRT decomposition, and bone hierarchy evaluation.
  • Implement floating-point bone texture and vertex-shader skinning.
  • Apply replay position, facing, animation index, and animation frame.
  • Add integer-frame clock, play/pause, stepping, and scrub.
  • Add original, fit, and follow camera modes.
Exit gate: 600 consecutive frames play at 60 Hz; pose matrices match C fixtures; no frame-image requests occur.
Phase 4 — Complete replay sceneParity
  • Multiple ports, same-character matches, followers/Nana.
  • Items, lasers, shields, stocks, HUD, and debug overlays.
  • Dynamic stage events already present in parser data.
  • Missing assets and animations degrade visibly and safely.
  • Run full-match soak tests and context restore tests.
Exit gate: sample replays complete without errors; camera modes work throughout; visual discrepancies are enumerated rather than hidden.
Phase 5 — Live WebSocket modeRollback-safe
  • Implement handshake, snapshot, batched frames, replacement, and game-end messages.
  • Add sequence-gap recovery and reconnect.
  • Test artificial latency, reordering, disconnect, duplicate messages, and rollback.
  • Expose live buffer depth and connection state separately from playback.
Exit gate: rollback replacements converge to the same final state as parsing the completed SLP.
Phase 6 — Default and removalDelete only after proof
  • Ship GPU renderer behind a query flag, then opt-in toggle, then default.
  • Collect errors, frame timing, asset failures, and context-loss metrics.
  • Retain C reference endpoints for one release window.
  • Remove raster-frame playback code and prefetch cache after acceptance.
Exit gate: GPU mode is stable as default and the raster transport has no remaining product dependency.

Visual differential workflow

  1. Render a fixture with the C reference renderer at a fixed camera.
  2. Render the same frame with WebGL2 at identical dimensions and camera.
  3. Capture the canvas.
  4. Compare per-pixel and structural similarity.

15Rollout and cutover

  1. ?renderer=webgl2 development path; existing renderer remains default.
  2. Internal visual/performance fixture suite must pass.
  3. Add user-visible renderer toggle and collect client errors.
  4. Make WebGL2 default while retaining ?renderer=software.
  5. After a stable window, remove frame prefetch, frame decoding worker, and raster playback endpoints.
  6. Keep a command-line/reference C renderer for golden-image generation.
First vertical slice: load one completed Fox vs. Falco replay on Final Destination, download its timeline and three reusable assets, draw textured animated fighters and the stage in WebGL2, play 600 consecutive frames at 60 Hz, and allow free camera pan/zoom—with zero frame-image requests. Do not broaden scope until this passes.

16Definition of done

  • Completed replay playback is fully local after initial state/assets load.
  • Live mode is batched, sequence-safe, reconnectable, and rollback-correct.
  • WebGL2 reproduces accepted C reference poses and stage output.
  • Playback clock advances exactly 60 replay frames per second without drift.
  • Camera is locally controllable in every playback state.
  • Measured performance and bandwidth meet the budgets above.
  • Raster-frame streaming is no longer used by the product path.
  • The old playback implementation is removed, not merely disabled forever.
